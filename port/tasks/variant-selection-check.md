# Задача: проверить, какой вариант шейдера Unity реально выбирает для каждого материала

## Контекст

Приватный порт Enter the Gungeon (Unity 2017.4.27f1) в WebGL 2. Корень: `C:\Users\pooky\Desktop\vm\etg`.
Сначала прочитай `README.md` и `port/README.md` целиком — особенно «Shaders», «Differential test», «D3D11-vs-GLES A/B
test» и список багов декомпилятора (баг 17 — прямой предшественник этой задачи).

Шейдеры игры есть только как байткод DX11. USCSandbox (`tools/src/USCSandbox` + `port/patches/uscsandbox-fixes.patch`)
декомпилирует их в CG (`bash port/decompile_shaders.sh` → `tools/uscs/out/`), `port/fix_shaders.py` правит под gles3,
`port/apply.sh` кладёт в Unity-проект `ripped/ExportedProject`. Каждый проход декомпилированного шейдера — это
`#pragma multi_compile ...` плюс цепочка `#if A && B ... #elif ... #else ... #endif`: по одной ветке на вариант
оригинала (условие — ключевые слова варианта), последняя ветка — `#else` без условия.

Что уже проверено:
- `bash port/shaderdiff.sh`: каждая ветка, скомпилированная *с ключевыми словами своего варианта*, считает то же, что
  оригинальный DXBC (3068/3068).
- `bash port/abtest.sh`: галерея материалов на D3D11 и GLES совпадает (остался только шум точности).

## Чего не видит ни один тест

Какая ветка `#if` выполняется в игре. Unity выбирает вариант по включённым ключевым словам (материала + глобальным +
выставленным движком: DIRECTIONAL/POINT/SPOT/..., LIGHTPROBE_SH, VERTEXLIGHT_ON, SHADOWS_*) среди комбинаций,
которые порождают строки `#pragma multi_compile/shader_feature`. Если наборы в прагмах не совпадают с настоящими, Unity
компилирует комбинацию, под которую не подходит ни одно условие, и молча выполняется `#else` — код другого варианта.
Так было с багом 17: точечные огни на LitCutoutUber выполняли DIRECTIONAL_COOKIE-код. Нашёлся он случайно — только
потому, что на D3D11 и GLES у текстуры затухания разный формат. Ошибка, одинаковая на обоих API, не видна никому.

Возможные причины кроме перемешанных наборов: ключевые слова материала, которых нет в прагмах (тогда Unity их
игнорирует); `shader_feature`, вырезаемые из сборки (в редакторе вариант есть, в браузере — нет);
порядок наборов/ключевых слов (Unity берёт первое ключевое слово набора, если не включено ни одно); ветки, условие
которых — подмножество условия более ранней ветки; `#else`, куда попадают комбинации, которых в оригинале не было.

## Цель

Для каждого материала проекта (`Assets/**/*.mat`) и каждого прохода его шейдера, при каждом наборе ключевых слов
движка, который реально бывает в игре, выяснить:
1. какой вариант *оригинала* выбрала бы игра (эталон — `tools/uscs/dump/<шейдер>/variants.json`: проход, стадия,
   ключевые слова каждого оригинального варианта);
2. какая ветка `#if` декомпилированного шейдера выполняется в Unity на самом деле;
3. совпадают ли они. Отчёт — несовпадения, сгруппированные по шейдеру и причине; плюс что не удалось проверить.

## Подход (предложение, можешь лучше)

**Статический проход (быстро, без Unity).** Python в `port/`: из прагм каждого CGPROGRAM построить все комбинации
ключевых слов, для каждой вычислить, какая ветка `#if` сработает (условия — простые `&&` макросов), и сравнить с
вариантом из `variants.json`. Найти: комбинации, падающие в `#else`, хотя в оригинале для них есть свой вариант;
ключевые слова материалов (`m_ShaderKeywords` в `.mat`), которых нет ни в одной прагме; материалы, чьи комбинации не
существовали в оригинале. Это дешёвая первая сетка, но она опирается на *предположение* о том, как Unity выбирает
вариант.

**Эмпирический проход (проверка предположения).** Тот же приём, которым был подтверждён баг 17: инструментированная
копия шейдера, где каждая ветка `#if` (включая `#else`) пишет в `SV_Target` свой номер цветом, а остальные проходы —
чёрный/ноль, чтобы цвет декодировался однозначно (иначе аддитивный проход смешивается с базовым и насыщается).
Рисовать инструментированные копии через инфраструктуру `EtgAbTest.cs` (`port/UnityAssets/Editor/EtgWebBuild/`):
квад в RenderTexture, setups dark/dir/point/spot/cookie дают движковые ключевые слова света. Читать номер ветки из
пикселей, где проход точно рисовал. Batchmode, одного API достаточно (`-force-d3d11` быстрее), прогон ~1 минута.
- Копии и материалы-двойники создавай во временной папке проекта (например `Assets/Editor/EtgWebBuild/_variants/`) со
  своими `.meta` (GUID задаёшь сам; материал-двойник = копия `.mat` с подменённым GUID шейдера) и удаляй после.
  Никогда не меняй оригинальные `.shader`/`.mat` в проекте.
- Учти: прогон в редакторе компилирует варианты на лету, а сборка вырезает `shader_feature`, которые не включены ни в
  одном материале. Отметь отдельно ветки, которые в редакторе выбираются, а в сборке пропали бы.
- ForwardBase-ключевые слова (`LIGHTPROBE_SH`, `VERTEXLIGHT_ON`, `SHADOWS_SCREEN`) зависят от сцены: в галерее
  `VERTEXLIGHT_ON` и тени не включаются (свет ForcePixel, тени выключены). Если это мешает — добавь setup с
  неважными (vertex) огнями; тени — по возможности, иначе отметь как непроверенное.

## Подсказки и подводные камни

- fxc не раскрывает функциональный макрос сразу после `.` (см. `ETG_ATTEN` в `fix_shaders.py`) — если будешь
  генерировать код с макросами.
- В `.shader` ветки вершинных и пиксельных программ — две отдельные цепочки `#if` (`// FORWARD:DX11VertexSM40` и
  `// FORWARD:DX11PixelSM40` в комментарии условия); у каждой свой `#else`. Проверяй обе: вершинная ветка тоже может
  быть чужой (позиции, интерполянты).
- Внутри веток бывают вложенные `#if` от `fix_shaders.py` (`#if UNITY_LIGHT_PROBE_PROXY_VOLUME`, `#if
  !UNITY_UV_STARTS_AT_TOP`) — не путай их с ветками вариантов (у вариантов в конце строки комментарий с типом
  программы).
- Шейдеры из Always Included Shaders (Graphics Settings) идут в данные плеера; для них важно, что попадает в сборку.
- Unity должен быть закрыт для batchmode (lockfile) — попроси пользователя. `apply.sh` — только при закрытом Unity.
  Лог: `-logFile` в `port/build/...`, и `%LOCALAPPDATA%\Unity\Editor\Editor.log` — читай сам.
- `.gitignore` — белый список: исходники в `port/` попадут, `port/build/` — нет.

## Ограничения

- Ничего не коммить и не публиковать без явной просьбы. Файлы игры и рип защищены авторским правом, проект приватный.
- Не трогай `C:\Program Files\Unity\...`.
- Исправления — в USCSandbox (`tools/src/USCSandbox`, потом `git diff HEAD > port/patches/uscsandbox-fixes.patch`
  из его каталога) или в `fix_shaders.py`. После правок: `bash port/decompile_shaders.sh`, `bash port/shaderdiff.sh`
  (должен остаться 3068/3068), `bash port/abtest.sh` (не должно появиться новых «differs»), допиши баг в список в
  `port/README.md`. Не меняй порядок ключевых слов в наборах без причины: при отсутствии включённого Unity берёт первое.

## Критерии готовности

1. Одна команда (скрипт в `port/`) строит отчёт: для каждого материала/прохода/набора движковых ключевых слов —
   ожидаемый вариант оригинала, выполняемая ветка, совпадение; несовпадения сгруппированы по шейдеру и причине.
   Явно перечислено, что не проверено и почему.
2. Чувствительность: если временно вернуть старую группировку наборов в USCSandbox (до бага 17), отчёт показывает
   LitCutoutUber/LitBlendUber/LitCutoutUber_ColorEmissive/BurnableSprite/DisplacerBeast с point/spot светом как
   несовпадение; с текущей — нет.
3. Найденные несовпадения исправлены или описаны с причиной; README обновлён.
